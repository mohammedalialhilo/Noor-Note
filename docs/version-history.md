# Version history

**Status: PARTIAL.** Note history is available locally from the note actions menu. The dialog lists saved checkpoints, previews exact Markdown, compares a checkpoint with the current note or another checkpoint, and shows inline or side-by-side line changes plus recorded metadata changes. Restoring requires confirmation. Duplicating creates an ordinary new Markdown note.

Each checkpoint has a stable UUID, vault and note UUIDs, a note revision number, timestamp, kind, title, path, Markdown, and SHA-256 checksum. New checkpoints also record folder ID, aliases, and properties. `origin` and optional `deviceId` allow local and future cloud checkpoints to use the same validated schema; `restoredFromId` links a restore checkpoint to its source. Older checkpoints remain readable without metadata. Restoring one of these older records restores title and Markdown while retaining the current folder, path, aliases, and properties.

Autosaves within five minutes replace the latest autosave checkpoint. Manual saves, rename and move operations, and restores create separate checkpoints. This avoids one snapshot per keystroke. The editor flushes pending writes before opening history or applying a history action. Restore checks the current note revision and the archived Markdown checksum, reserves the archived path, and writes the note and new restore checkpoint in one IndexedDB transaction. A path collision or missing archived folder rejects the operation without changing the note. The previous current checkpoint remains available for another restore. Duplicating a revision uses a collision-safe new path and copies recorded metadata when available.

Full-vault and folder ZIP exports include selected notes' checkpoints as separate `.noor-history/UUID.json` entries named in the optional manifest `revisions` list. Markdown note files remain ordinary `.md` files. Import validates each checkpoint and checksum, remaps note, vault, folder, revision, and restore-source IDs, then writes the imported history plus a checkpoint for the imported current note. Older ZIPs without a `revisions` list remain valid. ZIP import retains its 10,000-entry and size guards; very large histories may require smaller exports or a future streaming archive version.

History is currently kept until the note is permanently deleted. The future retention policy should be a per-vault setting with a `keep all` default and optional age/count bounds. Pruning must preserve the current checkpoint, at least one recovery checkpoint, and any restore source referenced by a retained checkpoint; it should run after a successful backup or cloud acknowledgement. No retention controls or pruning run today.

Cloud sync currently sends whole *current note* snapshots and operation revision IDs, not this checkpoint history. The shared checkpoint schema can represent future cloud records, but cloud history transfer, remote retention, and merge ordering are **not implemented**. A device that pulls a note does not receive its other device's local checkpoints. Local ZIP export is the supported history backup path.
