# Backup and recovery

Open **Settings → Your data → Backup Center**. The current vault can be exported as a manual Noor Note ZIP and downloaded. Backup Center verifies the manifest version, expected files, entry sizes, ZIP signatures, note checksums, and revision checksums before offering the download or restore. A restore verifies the archive again, creates a new local vault, and leaves the current vault untouched. The importer rolls back a newly created vault if import fails. Keep the downloaded ZIP outside browser storage.

For encrypted cloud backup, sign in to a configured Supabase project and enter a separate passphrase of at least 12 characters. Noor Note first creates and verifies the ZIP locally. The browser derives an AES-256-GCM key with PBKDF2-HMAC-SHA-256 (600,000 iterations, random 128-bit salt), encrypts 4 MiB chunks with unique random IVs and authenticated manifest/chunk metadata, then uploads the manifest last. Each snapshot is independent of normal sync. The private `noor-note-backups` bucket uses owner-only Storage policies. The cloud can see account ID, backup ID, creation time, archive size, chunk count, and access patterns, but not the vault name or content. Opening a cloud backup requires its passphrase and verifies the decrypted ZIP before offering restore or download. A lost passphrase cannot be recovered. Downloading an unlocked ZIP produces a plaintext file: store it securely.

Cloud backup currently accepts ZIPs up to 512 MiB and lists at most 1,000 completed snapshots. An upload interrupted before its final manifest does not appear as completed, although its encrypted chunks can remain in Storage and count toward quota; server-side orphan cleanup and snapshot retention are future work. This browser implementation does not provide scheduled local backups: the browser may suspend or close Noor Note, and periodic background sync is not reliably available. There is no simulated schedule.

Backup verification proves that an archive matches its own manifest and ZIP checks. It cannot prove that source data was correct when exported or that a cloud provider will retain it indefinitely. Keep more than one copy and periodically test a restore into a new vault. This feature has embedded tests for archive checks, encryption/tamper resistance, upload commit order, and Storage RLS. A deployed Supabase project and real browser restore still need operational verification.
