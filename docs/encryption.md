# End-to-end encryption

**Status: PARTIAL.** Noor Note can encrypt a new, previously unsynced private vault before enabling cloud sync. Local Markdown remains readable in this browser. Encrypted sync requires the Supabase [encryption migration](../supabase/migrations/202609290002_noor_e2ee.sql) after the base sync migration. The migration fixes each cloud vault's encryption mode at creation and rejects plaintext records in encrypted vaults. Existing plaintext cloud vaults cannot be converted retroactively because old snapshots, backups, logs, and uploaded attachments may remain on the server. Create a new vault for encrypted sync.

## Threat model

| Data | Encrypted before upload? | Visible to Supabase |
| --- | --- | --- |
| Vault name and settings; folder names and paths; note titles, Markdown, properties, aliases, Trash state | Yes, inside authenticated record ciphertext | Record kind, vault and item UUIDs, owner account, device UUID, server version, sequence, write time, ciphertext size and hash |
| Attachment name, MIME type, path, metadata, and bytes | Yes; bytes are uploaded as authenticated ciphertext with generic MIME type | Attachment UUID, ciphertext length and hash, upload timing, owner/vault routing path |
| Vault recovery envelope | Vault key is wrapped under a random 256-bit recovery code | Wrapped key, key epoch, nonce, vault UUID; not the recovery code |
| Device public keys and recipient envelopes | Public key is public; vault key in envelopes is encrypted | Device IDs, public keys, fingerprints, recipient/owner IDs, key epoch, envelope size |

Supabase Auth still sees account data and can link vault and device IDs to an account. Supabase Storage and database administrators can delete, withhold, reorder, or replay ciphertext, and can observe access patterns. AES-GCM detects modification of a record or attachment, but sync's current-version protocol does not prevent a malicious server from withholding the newest valid record. The static Noor Note host can see page requests and connection metadata; it does not receive keys through an application API. A compromised host, malicious browser extension, or injected script can read unlocked content and passphrases. E2EE does not protect against those threats. Local vault bodies, local history, queued sync snapshots, and ordinary vault ZIP exports remain plaintext in browser storage or exported files. Use the device's disk protection and guard exported ZIPs.

Noor Note currently has no application server that receives vault plaintext. The optional AI system is separate from cloud sync and requires its own explicit scope review. Future hosted features must not silently bypass this encryption boundary.

## Keys and format

Each encrypted vault has a random 256-bit AES key and a positive key epoch. Web Crypto AES-GCM uses a fresh 96-bit nonce and 128-bit authentication tag per record or attachment. Additional authenticated data binds the vault UUID, epoch, record kind, and item UUID to the ciphertext. The wire envelope is versioned. Attachment ciphertext has a versioned binary header with its epoch and nonce. Only ciphertext checksums are used in Supabase object paths; the plaintext attachment checksum remains inside the encrypted record. Record and attachment formats use established Web Crypto primitives specified by [W3C Web Cryptography](https://www.w3.org/TR/webcrypto/) and [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final); the envelope is Noor Note's serialization format, not a new cipher.

The passphrase never goes to Supabase. A unique 128-bit salt and PBKDF2-HMAC-SHA-256 with 600,000 iterations derive a local wrapping key. This is the current [OWASP recommended PBKDF2 work factor](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); a weak passphrase can still be guessed offline if its wrapped key is stolen. A separate random 256-bit recovery code wraps the same vault key for another device. The code is displayed once before encryption is committed; the user must acknowledge saving it. Local IndexedDB stores the wrapped profile, and the cloud vault record carries only the recovery envelope. Unlocking imports the vault key as a nonextractable browser `CryptoKey` kept in this tab's memory. Closing or locking the tab drops Noor Note's reference; JavaScript garbage collection controls final removal.

The device-key primitive generates a nonextractable P-256 ECDH private key and exportable public key. An ephemeral sender key, ECDH, and HKDF-SHA-256 derive a one-use AES-GCM wrapping key for a recipient device. A recipient envelope names a public-key fingerprint. The sender must verify that fingerprint through an authenticated channel outside Supabase before sharing; otherwise a malicious key directory could substitute a key. The migration creates owner-readable, immutable public-key records and sealed-envelope tables; a future membership policy must limit which verified recipients' keys can be fetched. Device registration, invitations, shared-vault authorization, and member access are **not implemented**. No shared plaintext password is stored in a database.

## Recovery and loss

On a new device, enter the recovery code and set a new local passphrase. The client decrypts the wrapped vault key, checks the authenticated cloud vault record, then downloads and decrypts content. An incorrect code imports no vault. If the local wrapped key profile is lost but the vault remains in this browser, Settings offers recovery for that vault ID. A durable `syncEncryptionMode` marker in the local vault blocks plaintext synchronization while the key profile is missing. If the cloud vault was never uploaded, that recovery envelope does not yet exist; the user must retrieve the original local key profile or work from a new vault. Resetting the Supabase account password does not recover encryption keys. If both the passphrase and recovery code are lost, cloud ciphertext cannot be decrypted by Noor Note or Supabase; an existing local plaintext vault or an earlier plaintext ZIP may still contain the data. Recovery codes should be kept outside the browser profile.

## Rotation design

The wire format and recipient envelopes carry a key epoch. Safe vault-key rotation will create a new random key, distribute new envelopes only to authorized devices, re-encrypt every record and attachment, verify all new ciphertext before switching the active epoch, retain old keys during an interrupted migration, and remove old ciphertext and envelopes after every device has migrated. Member revocation must rotate the key and cannot undo copies a removed member already downloaded. **Automated vault-key rotation, recovery-code replacement, and member revocation are not implemented yet.** Do not treat a compromised vault key or recovery code as revocable in the current release.

## Current bounds

Encrypted attachment processing currently uses whole-file Web Crypto and is limited to 64 MiB per file; a larger attachment remains local and reports a sync error for that item. The server sync-record payload limit is 2 MB, which includes base64 ciphertext. Live Supabase SQL/RLS/Storage verification and an independent cryptographic review are still required. Plaintext revision history and other structured objects are not currently synced by the base cloud protocol.
