# Realtime collaboration

**Status: PARTIAL.** Two signed-in users can edit the Markdown body of the same note through Yjs after the vault owner enables cloud sync, invites another verified account as an Editor or Admin, and the recipient accepts. Apply [migration 003](../supabase/migrations/202609290003_noor_collaboration.sql) and [migration 004](../supabase/migrations/202609290004_noor_sharing_permissions.sql) after the earlier sync migrations. The recipient opens Settings → Browse cloud vaults to download the shared vault. Members receive the full plaintext vault, including its attachments; sharing is unavailable for encrypted vaults until secure recipient-key distribution is implemented.

## Data flow

The cloud note snapshot carries a `collaborative` marker. Its Markdown at activation becomes the initial Yjs document. From then on, CodeMirror binds directly to `Y.Text`; the canonical local note remains Markdown and is updated through the normal autosave path. Individual Yjs updates are written to IndexedDB before an upload attempt. Supabase Postgres stores the initial update and an append-only update log; a private Supabase Realtime channel broadcasts only new sequence numbers. Clients fetch durable updates under row-level security. The same private channel sends ephemeral Yjs awareness updates for remote cursors and selections; Supabase Presence shows connected account identities. Presence is not a durable edit log. Yjs updates and local Markdown are plaintext in their respective stores for these shared vaults.

On reconnect the client fetches missed sequence numbers, applies them idempotently, and retries locally queued updates. A device can edit offline after it has opened and cached the collaborative document once. A newly signed-in device without that cache must connect before editing the shared note. Pausing cloud sync also pauses collaborative transport while retaining the local journal. The normal note-snapshot sync no longer uploads the collaborative Markdown body after a Yjs document is cached on the device. ZIP and single-note exports still read portable Markdown from local storage.

## Access and limits

Owners and Admins can manage eligible members in Settings. Owner, Admin, and Editor can append Yjs updates and send private Broadcast events. Commenter and Viewer can read collaborative documents and observe presence but cannot append edits; Commenter can add a separate cloud comment. Role checks are performed in Postgres; see [sharing and permissions](sharing-permissions.md). Removing a member blocks new database requests, but Realtime may retain cached authorization until the connection refreshes; a removed member can retain data already downloaded. Use short Auth token lifetimes and test revocation against a live project before broad deployment.

The Yjs log currently has no compaction or retention policy, and only the Markdown body is collaborative. The title is locked while collaboration is active. Other metadata changes, note deletion, and refactoring a collaborative note from another surface are not coordinated by Yjs. Collaborative editing is unavailable for E2EE vaults and local-only accounts. SQL policies and Realtime behavior have not yet been verified against a live Supabase project. See [security](security.md) and [sync protocol](sync-protocol.md).
